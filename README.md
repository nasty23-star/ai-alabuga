# Арена переговоров

Telegram Mini App: текстовый тренажёр переговоров. Пользователь выбирает сценарий, задаёт цель и границы условий, ведёт диалог с ИИ-собеседником и получает разбор после завершения. Пока бэкенд не подключён, клиент работает на встроенном моке с тем же контрактом, что и HTTP-клиент.

Визуальный бренд на главном экране — «Вершина»: переговоры поданы как восхождение.

## Стек

| | |
|---|---|
| UI | Vue 3, Composition API, `<script setup>` |
| Состояние | Pinia |
| Маршруты | Vue Router, `createWebHashHistory` |
| Сборка | Vite 7, TypeScript (strict), `vue-tsc` |
| Линтер | oxlint |
| Пакеты | pnpm 11 |
| Шрифт | Inter (Google Fonts) |
| Оболочка | Telegram Web App (`telegram-web-app.js`) |

Бэкенда в репозитории нет. Слой `Api` один: экраны не знают, мок это или HTTP.

## Запуск

```bash
pnpm i
pnpm dev
```

Откройте адрес из вывода Vite (обычно `http://localhost:5173`). Если порт занят, Vite возьмёт следующий. Сервер слушает `host: true`, поэтому доступен и по адресу в локальной сети.

В Telegram Mini App укажите этот адрес как URL веб-приложения. Маршруты hash-based (`/#/scenarios`), базовый путь сборки — `/ai-alabuga/`.

```bash
pnpm lint
pnpm build
pnpm preview
```

`build` сначала проверяет типы (`vue-tsc --noEmit`), затем собирает `dist`. Публикация на GitHub Pages:

```bash
pnpm deploy
```

Скрипт `predeploy` сам запускает сборку. Каталог `dist` отдаётся через `gh-pages`.

## Конфигурация

Скопируйте `.env.example` в `.env`. Файл `.env` в git не попадает.

| Переменная | Значения | Смысл |
|---|---|---|
| `VITE_API_MODE` | `mock` (по умолчанию) или `http` | Какой клиент поднять при старте |
| `VITE_API_BASE_URL` | URL без завершающего `/` | База HTTP-клиента, например `http://localhost:8000` |

Режим выбирается один раз при импорте `src/api/index.ts`. Смена `.env` требует перезапуска Vite.

Алиас `@` указывает на `src/`.

## Как устроен клиент

```
index.html          Telegram SDK и цвета шапки до монтирования Vue
src/main.ts         Pinia, роутер, initTelegram, обработчик 401
src/App.vue         сплэш, автовход Telegram, нижняя навигация
src/router          охрана сессии и онбординга
src/stores          сессия и тумблер геймификации
src/api             контракт, HTTP, SSE, мок
src/telegram.ts     MainButton, BackButton, профиль
src/views           экраны
src/gamification    правила бейджей
```

Интерфейс вписан в колонку шириной до 390px на фоне `#e7edf6`. В Telegram на `documentElement` вешается класс `tg-app`, шапка `#c5daf8`, фон `#f5f7fb`, кнопка `#1a5cff`. Класс `.tg-hide` на дублирующих кнопках есть, но правило скрытия в `styles.css` закомментировано: в мини-приложении видны и свои кнопки, и MainButton.

При старте сплэш держится минимум 900 мс. За это время:

- если есть профиль Telegram и логин сессии не `tg:<id>`, клиент вызывает `signInTelegram` и уводит на приветствие, сценарии или онбординг;
- если сессия уже есть, обновляет аккаунт через `GET /api/account`. Ошибка обновления сессию не сбрасывает.

Ответ `401` сбрасывает сессию и возвращает на `/auth?next=<текущий путь>`.

## Маршруты

История — hash, чтобы Mini App и GitHub Pages не зависели от серверных rewrite.

| Путь | Экран | Доступ |
|---|---|---|
| `/auth` | Вход, регистрация, гость | публичный, без нижней навигации |
| `/welcome` | «С возвращением» | только вернувшийся и уже прошедший онбординг |
| `/onboarding` | Имя и сферы | обязателен, пока онбординг не отмечен |
| `/` | редирект на `/scenarios` | |
| `/scenarios` | Главная | |
| `/scenarios/pick` | Выбор темы | |
| `/wizard/:scenarioId?` | Мастер перед диалогом | без нижней навигации |
| `/negotiations/:id` | Чат | без нижней навигации |
| `/negotiations/:id/debrief` | Разбор | |
| `/history` | Список прохождений | |
| `/settings` | Профиль | |
| `/s/:token` | Публичный разбор | без входа и без навигации |

Нижняя навигация: Сценарии, Новые переговоры, Разбор, Профиль. Её нет на сплэше, до конца онбординга, на `bare`-экранах, в чате и в мастере.

Охрана:

1. Публичные маршруты пропускаются. Уже вошедший на `/auth` уходит в онбординг, на приветствие или в сценарии.
2. Без токена путь запоминается и открывается `/auth?next=...`.
3. Без онбординга любой закрытый экран, кроме самого онбординга, перенаправляется туда.
4. Вернувшийся пользователь один раз за загрузку приложения попадает на `/welcome`, если сам туда не шёл.

## Сценарий пользователя

1. **Вход.** Экран-герой, затем логин и пароль (от 6 символов). Можно войти, зарегистрироваться или пропустить как гость. В Telegram форма не показывается: вход идёт по `initData` и профилю WebApp.
2. **Онбординг.** Два слайда, затем имя (пустое сохраняется как «Мистер X») и сферы. «Позже» ставит флаг онбординга локально, без записи сфер. Имя в ответе авторизации сразу считает онбординг пройденным — у пользователя Telegram с именем слайды пропускаются.
3. **Приветствие.** Только повторный вход. Кнопка «Тренироваться» открывает историю.
4. **Главная.** Приветствие, «Новое общение», «Свой собеседник» (мастер с `?persona=custom`), карточка последнего разбора. Бейджи видны, только если геймификация включена.
5. **Выбор сценария.** Темы с сервера. Берётся первый вариант темы (`theme__sphere`) и открывается мастер. Список сфер фильтруется профилем: пустой список сфер означает все пять.
6. **Мастер**, четыре шага: цель, 2–4 условия (граница, идеал, вес), заметки и BATNA, собеседник. Старт создаёт переговоры и открывает чат. Предыдущие активные переговоры этого пользователя мок переводит в `interrupted`.
7. **Чат.** Реплики, потоковый ответ, предложение сделки, «Уйти». Лимит реплики — `max_utterance_chars` (в моке 1200). Завершённые переговоры сразу открывают разбор.
8. **Разбор.** Самооценка (шкалы 1–7 и два текста) живёт только в экране и на сервер не уходит. Дальше метрики, глоссарий, ссылка руководителю.
9. **История.** Страницы по 20, курсор — id последнего элемента страницы. Завершённые открывают разбор, активные — чат. Прерванные в списке есть, отдельного экрана у них нет.
10. **Профиль.** Имя, сферы, тумблер геймификации, выход, закрытие мини-приложения. Гость может задать логин и пароль: история остаётся, `is_guest` становится `false`.

## Сферы, темы и условия

Сферы: `procurement` закупки, `sales` продажи, `hiring` найм, `management` управление, `founder` основатель.

Темы мока: размещение заказа, скидка у подрядчика, повышение зарплаты, продление контракта, бюджет проекта. Идентификатор сценария — `theme__sphere`, например `order_placement__procurement`. Сочетание `salary_raise` + `founder` отсутствует.

Типы условий и диапазоны: цена и бюджет (₽, до 100 млн), скидка (0–50%), объём, сроки оплаты и поставки, срок контракта, гарантия, время реакции, люди в команде, зарплата, премия, пересмотр через N месяцев.

Валидация условий в моке:

- от 2 до 4 пунктов;
- тип известен и не повторяется;
- граница и идеал не совпадают;
- оба числа внутри диапазона типа.

Вес: `low` 0.7, `medium` 1, `high` 1.4. Выгода сделки — среднее взвешенное приближение согласованного значения к идеалу от границы, потолок 100. Согласованное значение в моке — середина между границей и идеалом.

## Собеседники

Готовые персоны: `toxic_cpo` («Токсичная CPO»), `busy_ceo` («Занятой CEO»). Третья — `custom`, карточка на аккаунт.

Карточка: имя, роль, обращение (`formal` / `informal`), длина ответа (`short` / `medium` / `long`), формальность 0–1, черты, до 5 фраз не длиннее 200 символов, источник `manual` или `cognico`.

Импорт `POST /api/counterpart-profile/import` с `{ source: "cognico", person_id }` в моке возвращает карточку «Ирина». `person_id: "unavailable"` отвечает `503 source_unavailable`.

Фазы диалога: `opening` → `exploration` → `bargaining` → `closing`. Статусы: `active`, `finished`, `interrupted`. Исходы: `deal`, `partial_deal`, `no_deal`. Мок выставляет только `deal` и `no_deal`.

Лимит мока — 16 ходов игрока. Каждый четвёртый ход или реплика с `/deal` предлагает сделку. `/leave` завершает без сделки и шлёт `counterpart_left`. `/fail` обрывает поток, ход не записывается. На 16-м ходе без сделки — `turn_limit_reached` и `no_deal`.

Принять сделку можно только пока есть `pending_deal`. Иначе `409 no_converged_terms`. Отклонение возвращает фазу `bargaining` и снимает предложение.

## Разбор и шаринг

Разбор доступен только у `finished`. Метрики: `own_outcome`, `batna_gain`, `reservation_point_discipline`, `concession_discipline`, `open_question_ratio`, `filler_density`. У каждой есть зона `bad` / `normal` / `good`, доступность и `origin` (источник порога: academic, practice, expert_estimate, arithmetic). Без сделки первые две метрики недоступны. В моке часть чисел фиксирована и не считается по тексту.

Есть один `turning_point`: утверждение, эффект, совет и цитата хода.

Ссылка: `POST /api/negotiations/:id/shared-result` с `ttl_hours` и `include_transcript`. В интерфейсе сроки 24 часа и 30 дней (720 часов). Ответ — `{ id, url: "/s/<token>", expires_at }`. Клиент собирает абсолютный адрес как `origin + BASE_URL + # + path`. Отзыв — `DELETE /api/shared-results/:id`. Публичное чтение не требует токена. Отозванная или просроченная ссылка — `410`.

## Геймификация

Тумблер в профиле, хранение отдельно на логин: `arena-gamification:<login>`. Гость с пустым логином тоже имеет свой ключ. Пока тумблер выключен, бейджи не запрашиваются и не рисуются.

Бейджи считаются на клиенте по списку переговоров, не по отдельному API:

| id | Условие |
|---|---|
| `first-round` | есть завершённое прохождение |
| `deal` | есть сделка |
| `strong` | выгода сделки от 70 |
| `series` | три завершённых |
| `return` | два завершённых |

На главной счётчик «дней» сейчас равен числу полученных бейджей, отдельной серии дней нет.

## Сессия и хранилище браузера

| Ключ | Что лежит |
|---|---|
| `arena-token` | Bearer-токен |
| `arena-login` | логин, у Telegram `tg:<id>`, у гостя пусто |
| `arena-account` | JSON аккаунта |
| `arena-onboarded` | `1` / `0` |
| `arena-gamification:<login>` | тумблер бейджей |
| `arena-mock-db` | вся база мока: пользователи, токены, карточки, переговоры, ссылки, кэш идемпотентности |

Пароли мока лежат в `localStorage` открытым текстом. Это заглушка, не модель боевого хранения.

`greetOnEntry` включается при входе по паролю и при `returning: true` у Telegram. Регистрация и гость приветствие не показывают.

## Контракт API

Авторизация: `Authorization: Bearer <token>`. Создающие POST, где важен повтор, шлют `Idempotency-Key`: старт переговоров, ход, гость, принятие и отклонение сделки, уход, шаринг. Повтор того же ключа в моке возвращает уже сохранённый результат и не создаёт вторую сущность.

Ошибка:

```json
{ "error": { "code": "invalid_request", "message": "…", "details": {} } }
```

Клиент кладёт это в `ApiError` (`status`, `code`, `message`, `details`). `204` — пустой успех. `401` всегда вызывает выход.

Ход: `POST /api/negotiations/:id/turns` с `{ text }`. Если `Content-Type` ответа содержит `application/json`, это `TurnReplay` целиком. Иначе тело — `text/event-stream`. События разделены пустой строкой, поля `event:` и `data:` (JSON).

События потока:

| event | data |
|---|---|
| `thinking` | `{}` |
| `utterance_delta` | `{ text }` — кусок реплики, клиент склеивает |
| `turn_committed` | `{ turn_index, phase, turns_left }` |
| `deal_proposed` | `{ terms, summary }` |
| `counterpart_left` | `{ reason }` |
| `turn_limit_reached` | `{}` |
| `stream_failed` | `{ code, message }` — ход не зафиксирован |
| `done` | `{ phase, status }` |

Мок и при успехе отдаёт поток и возвращает клиенту `null` (реплика уже пришла дельтами). JSON-replay нужен HTTP-бэкенду, если он не стримит. При `stream_failed` черновик реплики возвращается в поле ввода, ключ идемпотентности не меняется.

Эндпоинты:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/auth/sign-up` | `{ login, password }` → `{ token, account }` |
| POST | `/api/auth/sign-in` | то же |
| POST | `/api/auth/telegram` | `{ init_data, id, first_name, last_name, username }` → ещё `returning?` |
| POST | `/api/auth/guest` | гостевой аккаунт |
| POST | `/api/auth/upgrade` | гость задаёт логин и пароль |
| POST | `/api/auth/sign-out` | отзыв текущего токена |
| GET, PATCH | `/api/account` | `display_name`, `spheres` |
| GET | `/api/issue-types` | справочник условий |
| GET | `/api/scenarios` | сферы и темы с вариантами |
| GET | `/api/scenarios/:id` | карточка: контекст, роли, дефолтные условия |
| GET | `/api/personas` | стоковые и `custom` |
| GET, PUT, DELETE | `/api/counterpart-profile` | карточка своего собеседника |
| POST | `/api/counterpart-profile/import` | импорт из Cognico |
| POST | `/api/negotiations` | старт: `{ scenario_id, persona_id, terms }` |
| GET | `/api/negotiations/:id` | состояние, ходы, `pending_deal` |
| GET | `/api/negotiations?limit&cursor` | лента |
| POST | `/api/negotiations/:id/turns` | ход |
| POST | `/api/negotiations/:id/deal/accept` | сделка |
| POST | `/api/negotiations/:id/deal/reject` | вернуться к торгу |
| POST | `/api/negotiations/:id/walk-away` | уйти без сделки |
| GET | `/api/negotiations/:id/debrief` | метрики и совет |
| POST | `/api/negotiations/:id/shared-result` | ссылка |
| DELETE | `/api/shared-results/:id` | отзыв |
| GET | `/api/shared-results/:token` | публичный разбор |

Коды, которые мок реально отдаёт: `weak_password`, `login_taken`, `invalid_credentials`, `already_registered`, `not_found`, `forbidden`, `too_few_issues`, `too_many_issues`, `unknown_issue_type`, `duplicate_issue`, `empty_range`, `value_out_of_range`, `too_many_phrases`, `phrase_too_long`, `source_unavailable`, `negotiation_finished`, `utterance_too_long`, `no_converged_terms`, `debrief_unavailable`, `link_revoked`, `link_expired`, `stream_failed`.

## Подключение бэкенда

В `.env`:

```
VITE_API_MODE=http
VITE_API_BASE_URL=https://api.example.com
```

Бэкенд должен повторять контракт выше: Bearer, `Idempotency-Key` на создающих POST, ход как SSE или как JSON `TurnReplay`, ошибки в `{ error: { code, message, details } }`. Экраны ходят только в `getApi()`.
